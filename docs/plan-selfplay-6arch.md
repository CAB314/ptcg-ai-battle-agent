# 6アーキタイプ相互自己対戦による自己強化 — 計画（2026-08-06 策定）

**目的**: v0（BC のみ）の6体を、6体相互のリーグで PPO 自己強化する。
**指標**: すべて **固定版 v0（`runs/opp_frozen_v0/`）を基準**とする。

---

## 0. 前提（実測で確認済み）

| 項目 | 値 | 根拠 |
|---|---|---|
| the cluster キュー制限 | **なし**（同時実行の上限なし・多数のノード・最大4日） | Slurm のパーティション設定 |
| ディスク | 共有ストレージに**十分な空き**。PPO 1run ≈ 1.1GB | `df` / `du` |
| PPO 速度 | **343 iter/h**（1GPU・28アクター） | 8/2 実測 |
| **BC→初回PPO の効果** | **vs 凍結BC H2H 61.5%（n=1,600）** | alakazam_ppo v1（7/17） |
| 現在の GPU 累計 | 約 24 時間 | 実験ログ |

**重要**: 8/2 の PPO v3 は「既に PPO 済みの方策への追加 PPO」で **互角（49.9%）** だった。
今回は **BC のみの方策への初回 PPO** なので、上表の 61.5% の方が近い前例。
ただし **プラトーは初回PPOでも早期に来る**（過去の観測: iter 400 以降ほぼ横ばい）ため、
長く回す設計にはしない。

---

## 1. 何と戦わせるか（リーグ構成）

各 run のリーグを **6体相互 + 自己対戦** に構成する。既存の league 機構をそのまま使う。

| バケット | 比率 | 中身 |
|---|---|---|
| latest（ミラー） | 0.40 | 自分の最新方策どうし（**自己対戦**） |
| snapshot | 0.25 | 自分の過去スナップショット（PFSP-lite） |
| **fixed（相互対戦）** | **0.35** | **他5体の v0** + Grimmsnarl(v1) + Mewtwo(v1) の計7 |

- fixed の 7 体は **v0 で固定**する。相互に動く相手にすると、
  「相手が弱くなったから勝率が上がった」のか「自分が強くなったのか」が**分離できない**。
  基準を動かさないのが測定の前提（8/4 に確認した「勝率はレート帯マッチングで50%に収束する」
  という交絡と同型の問題）。
- fixed 内の重みは **8/4 実測メタシェアに比例**させる。

**注意**: 「6体が互いに学習し合う」真のセルフプレイ・リーグにはしない。理由は上記の
測定不能性に加え、6体が同時に動くと**どの改善がどこから来たか特定できない**ため。
相互作用を見たい場合は、v1 完成後に「v1同士のリーグ」で第2ラウンドを回す（§6）。

## 2. 学習設定

- **anchor** = 各アーキタイプの v0（KL 正則化の基準）。これで v0 から離れすぎない。
- **TARGET_ITER = 1,000**（343 iter/h → **約3時間**）。
  過去の観測でプラトーは iter 400 以降なので 1,000 で十分。到達で自動停止。
- ガントレット有効（**8/2 に修正済み**の起動待ち・失敗時継続）。best 追跡と自動巻き戻しが効く。
- 安全装置: `--gpus=1` 固定 / learner 死亡の即時検知 / MAX_CHAIN / **投入後15分チェック必須**。

## 3. 実行計画（並列6本）

| 段 | 内容 | 所要 | GPU時間 |
|---|---|---|---|
| A | run 初期化（config/league/policy 配置）・疎通確認 | 0.5h | 0 |
| B | **PPO 6本を並列投入**（各 1,000 iter） | **約3h** | **18h** |
| C | v0 基準の測定（純CPU） | 1h | 0 |
| D | 相手プール差し替え → アブレーション再実行 | 0.5h | 0.2h |
| | **合計** | **約5h** | **約18.2h** |

**GPU 累計見込み: 約24h → 約42h。**

6本を同時に投入する（キュー制限なし・多数のノード）。同一ノードに載ると 28 actors × 6 で
CPU 競合するので、**`--exclusive` は付けず Slurm のノード分散に任せる**が、
段Aの疎通確認で1本だけ先に流して iter/h を実測し、想定より遅ければアクター数を下げる。

## 4. 合否判定（**事前に決める**）

v0 を基準に、**3つすべて**を満たしたら「強化成功」とする。

1. **同一デッキ・方策のみ差の H2H で v0 に勝ち越す**: n=1,200 で **勝率 ≥ 54%**
   （n=1,200 の SE は 1.44pp なので 54% は z≈2.8）。
   - ミラー戦は実力差が出にくいことが分かっているので、**これは必要条件であって十分条件ではない**。
2. **メタ加重フィールドで v0 を上回る**: 相手 = 他5体の v0 + Grimmsnarl + Mewtwo、
   8/4 シェア加重、各 6,000 戦で **Δ ≥ +1.5pp**。
   - **こちらを主指標とする**（8/4 の実測で「ミラー H2H はラダーを予測しない／
     field 加重は予測した」ことが分かっているため）。
3. **退行が無い**: v0 に対して**大きく負け越す対面が新たに生まれていない**
   （どの対面でも v0 比 −5pp 以内）。

判定に落ちた個体は **v0 のまま据え置く**（相手プールにも v0 を使う）。

## 5. 想定される結果と、その後の使い道

| 結果 | 確率の見立て | 使い道 |
|---|---|---|
| 6体とも強化成功 | 中 | 相手プール総入れ替え → アブレーション再実行の精度が上がる |
| 一部のみ成功 | **最も可能性が高い** | 成功分だけ差し替え。Garchomp は tval 60.5% と教師の一致が低く、伸びにくい可能性 |
| ほぼ全滅（プラトー） | 中 | **それ自体がレポートの結果**（「BC のみ→PPO でも伸びない」の追加証拠）|

**副次的な使い道**: Lopunny と Alakazam は現メタ各 14.9% で、
**我々の主力の最大の弱点**（ppo2 は対 Lopunny 0勝4敗）。ここが強く仕上がれば
**8/16 の提出候補**にもなる。ただし提出は別途ゲートを通す。

## 6. やらないこと / 次ラウンドの条件

- **6体が同時に学習し合うリーグはやらない**（§1 の理由）。
- v1 が出そろった後、**「v1 同士のリーグ」で第2ラウンド**を回すことは可能。
  ただし基準は常に v0 に置き、v0→v1→v2 の各段を独立に測る。
  第2ラウンドは **v1 で明確な改善が出た場合のみ**着手する（GPU 18h の追加）。

## 7. リスクと対策

| リスク | 対策 |
|---|---|
| 6並列で CPU 競合し iter/h が落ちる | 段Aで1本だけ実測してから残り5本を投入 |
| learner 即死（7/30 に4.5h浪費） | sbatch の watchdog + **投入後15分チェック** |
| 起動したまま気づかない（8/5-8/6 に8時間空費） | **完走まで自動で追う監視を必ず付ける**（今回は sbatch 内で全段連結） |
| PPO が v0 を下回る | ガントレットの自動巻き戻し。最終的には §4 の判定で据え置き |
| GPU 課金の膨張 | TARGET_ITER 自動停止。18h で打ち止め。超過しそうなら段Bを2本ずつに分割 |

## 8. 事前監査（2026-08-06 実施・Go判定）

実行前にコードパス（league/actor/learner/sbatch）を通し読みし、統合スモークテストを
ローカルと the cluster の両方で実施した。**判定: Go（下記修正を先に適用）**。

**発見した問題と修正:**

1. **fixed バケットに静的重みの機構がなかった** — `_pfsp_pick` は (1−EMA)² のみで抽選し、
   §1 の「メタシェア比例」は実装されていなかった。→ セルの `"w"` を乗数として実装
   （省略時 1.0 で従来挙動と互換）。
2. **`PPOConfig.league_*` / `deck_mix` は死に設定** — config に定義があるがどこからも
   読まれず、リーグ構成の唯一の源は league_state.json。config だけ変えると
   **黙って旧来のプール（ルール勢+自分のanchor）で学習が走る**ところだった。
   → `scripts/setup_selfplay_run.py` が league_state.json を直接生成する。
3. **v1特徴量の Grimmsnarl/Mewtwo を np_fixed に入れると即死する** — actor の
   np_fixed 経路は現行テーブルでエンコードするため、v1 の weights.npz は
   NpPolicy.load が None を返し assert 死 → supervisor が respawn し続ける
   （watchdog は learner しか見ないので止まらず、課金だけ続く）。
   → rule_agent 経路（`agents/grimmsnarl_ppo2` / `trmewtwo_ppo2`、vendored隔離）を使用。
   同一プロセスで現行モジュールと混在できることをスモークで確認（T2/T2b）。
4. **the cluster の ~/PTCGRL は git リポジトリではない** → 変更は scp + sha256 照合で配布
   （rsync のサイレントスキップ事故の再発防止）。
5. sbatch の cd フォールバックが旧パス `$HOME/ptcg` のままだった → PTCGRL に修正。
6. **メタシェアを 8/4 → 8/5 実測に更新** — Grimmsnarl 62%→30% と激変が続いており、
   fixed の w と decks.meta は 8/5 値で生成。

**GPU 枚数・並列化の結論:**

- 課金は `TRESBillingWeights=CPU=0.0,Mem=0.0,GRES/gpu=1.0` — **GPU のみ課金**。
- ただしサイトポリシーで **GPU 1枚あたり CPU 32 個が上限**（--cpus-per-gpu=64 は投入拒否を実測）。
  アクター増強には遊休 GPU を買う必要があり、+10〜20% の課金で壁時間 3h→1.7h の短縮にしか
  ならない（learner は単一GPU設計で 2枚目は必ず遊ぶ）。凍結まで 10 日あり壁時間に価値がない。
- **結論: 実証済みの 1GPU×28アクター×CPU32 を6本並列（計6GPU）が最適。**

**プリフライト:** 6 run × 7 fixed セル = 42 通りを actor と同一経路でロードし
各1戦実行 → **全て正常**（export parity も全 run argmax 100%）。
